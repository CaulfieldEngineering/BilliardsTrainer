### HDMI vs USB on the T3i — treat as EITHER/OR (researched 2026-07-28)

Joe's field observation ("HDMI doesn't work once USB is connected") is
confirmed by the sources, with one nuance:

- Canon's guidance + community consensus: EOS Utility (USB tether) and HDMI
  live view do NOT coexist on Rebel bodies; Canon documents the Rebel HDMI
  port as intended for PLAYBACK to a TV, so live-view-over-HDMI is an
  unsupported side effect (hence its fragility). The DIGIC 4 display path
  effectively drives one target at a time — same reason the rear LCD blanks
  when HDMI is plugged in.
- Nuance: the kill mechanism is a PTP session REDIRECTING liveview, not
  electrical exclusivity. Our own driver has both paths:
  `eos_ptp.start_liveview()` sets EVFOutputDevice=2 (PC) -> "HDMI goes dark";
  `ensure_hdmi_liveview()` sets EVFOutputDevice=1 (TFT/HDMI mirror) and was
  once validated at ~25fps out the dongle WITH the session held. So a careful
  client can coexist, but anything that switches LV to "PC" (EOS Utility,
  macOS ptpcamerad, a stray daemon, our own start_liveview) blacks out HDMI.
- RIG RULE: do not plug USB into the ceiling camera while HDMI is the feed.
  Any host that auto-claims the camera can kill the video mid-session. USB
  tether (~704 eff lines) remains an ALTERNATIVE to HDMI, never a companion.
- Sources: Canon Community (external monitor vs EOS Utility; Rebel T7 live
  view monitor threads), Canon support 8201003300 (T3i HDMI-to-TV page),
  DPReview thread 2956902.

### Recording frame-rate jitter (2026-08-02, Claude-web) — FIX IMPLEMENTED (needs on-rig eyeball)

Symptom (Joe): raw session recordings look good but have intermittent, almost
imperceptible micro-pauses — a frame briefly holds/stutters, then resumes.

Root cause is the **paced CFR writer** (`FfmpegWriter._pace` in
capture/videowriter.py, introduced in 88c3ceb). The pacer thread emits a frame
every `1/rec_fps` on a rigid wall-clock grid, but it samples whatever is in
`self._latest` at that instant (`write()` only overwrites `_latest`; it never
tracks frame identity). The thing PRODUCING those frames is the controller tick
(`_run_frame`), whose real cadence is irregular — each tick is
`camera.read()` + `preprocess_frame` + `pipeline.process()` (warp/track/annotate
render), and that per-frame cost swings with load (heavy scenes = more balls =
slower render; GC; async-detector results landing; the 150-frame feed-geometry
check). So the recorder is fed at *pipeline throughput*, not camera cadence.
Whenever a tick runs slower than `rec_fps`, no new frame has arrived and the
pacer re-emits the same frame → a brief hold; when ticks bunch, a frame is
dropped → a small jump. On smooth motion (a rolling ball) this beat between the
two free-running clocks is the micro-stutter. Non-integer rate ratios make it
worse (60fps camera decimated 60→30; 29.97/25 beating against 30).

The pacer was the right fix for the ORIGINAL problem it solved (audio drift —
it guarantees exact CFR so A/V stays aligned). So any fix MUST preserve
exact-CFR / audio alignment. The pacer is faithfully rendering a jittery
source; garbage-in, garbage-out.

IMPLEMENTED (branch claude/billiards-trainer-frame-jitter-lot28x). The fix is
PURELY a timing decouple — the recording's visual processing is UNCHANGED (Joe:
"the visual appearance of the video is fine, just the frame rate"; he wants the
letterbox crop + denoise/sharpen kept). Only the frame-timing SOURCE moved off
the CV loop. Changes:

- `ThreadedCameraSource.set_frame_sink(cb)` (capture/camera.py): the grab thread
  now hands EVERY frame to an optional sink the instant it arrives, at true
  camera cadence. Guarded (a sink throw can't kill the capture loop).
- Recording taps that sink (workers/controller.py `_record_frame_live`): live
  camera recording is written straight off the grab thread, fully decoupled from
  the CV tick. A busy pipeline (heavy scene, GC, detector results landing) can no
  longer starve the recorder into micro-stutter. The frame is preprocessed +
  cropped + denoised/sharpened/upscaled EXACTLY as before (same
  `_write_recording` + `FfmpegWriter`), so recordings look identical — the heavy
  filters run inside ffmpeg, not on the grab thread, so the tap stays cheap.
  Recorder state is shared across grab + controller threads, guarded by
  `_rec_lock`; the CV-tick-fed path remains only for non-live sources (video
  review / demo).
- videowriter.py is UNCHANGED from main (an earlier raw-encode variant was
  reverted once Joe confirmed the look was fine).
- The paced CFR writer stays (guarantees exact-CFR so audio stays aligned) — but
  it's now fed a STEADY camera-cadence stream, so its resample is ~1:1 with
  minimal dup/drop instead of beating against jittery pipeline output.

Tests: tests/test_recording_realtime.py (grab-thread sink dispatch/detach/throw-
safety; writer still applies its denoise+sharpen chain). Full suite green
locally. STILL NEEDS: Joe to eyeball a real session recording to confirm the

**ROUND 2 (2026-08-02 evening) — jitter persisted; the first fix was
incomplete.** Joe confirmed stutter on a real recording after the grab-thread
feed shipped. Honest post-mortem: round 1 fixed WHO feeds the writer but left
the rigid wall-clock pacer, and the "resample is ~1:1" claim above was wrong —
two nominally-equal free-running clocks (camera frame clock vs OS timer) still
beat, and arrival jitter around the fixed sampling instants flips frames
between ticks. Simulated on a realistic feed (±35% arrival jitter, 80ppm clock
skew, 5 min): the pacer produced **801 duplicated + 801 dropped frames** — a
hitch every couple of seconds, matching Joe's report exactly. Same feed through
the replacement: **zero**.

Fix (this round): the pacer thread is DELETED. `FfmpegWriter.write(frame, ts)`
now retimes each frame from its own CAPTURE timestamp into CFR output slots
(`_CfrRetimer`): slot = round((ts−t0)·fps); emit once per new slot, duplicate
only across real capture gaps (capped at 2s, then resync), drop only same-slot
bursts. A slow phase servo (ALPHA=0.05) centres arrivals mid-slot — absorbs
the first frame's arbitrary phase and tracks camera-clock skew — and a
host-clock drift clamp (±3 slots) keeps video duration pinned to real elapsed
time, so A/V sync is preserved by construction (output is still exactly
`fps` frames per wall-clock second; the audio path is untouched).

Threading also restructured: the grab-thread sink now ONLY enqueues
(frame, monotonic-ts) into a bounded queue (8); a dedicated `rec-writer`
thread does preprocess + encoder writes. So an encoder stall can never block
the grab thread (round 1 did blocking stdin writes + preprocess ON the grab
thread — auto white-balance there could slow capture itself; both now off it).
Teardown: sink off → sentinel → join → release, so the tail of the queue is
drained into the file.

Tests: `_CfrRetimer` unit tests (jittered steady feed → zero dup/drop after
servo settle; clock skew → no periodic beat; real gap → bounded dup fill;
same-slot burst → drop), plus an end-to-end ffmpeg encode (60 jittered frames
in → exactly 60 in the file). STILL NEEDS the same on-rig eyeball as before —
that is the only validation that counts.
